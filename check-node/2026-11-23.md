# 2026-11-23 学习报告（Task 3：P2 + I2）

## 一、学习范围

Task 3 对应 P2《Agentic RAG 产品设计》和 I2《向量数据库与 RAG》。

- **P2 从产品视角**回答：RAG 为什么会答不好、问题该归因到哪一层、验收标准怎么定。
- **I2 从工程视角**解释：Embedding、向量索引、混合检索、重排和评测为什么这样设计。

两篇合起来，正好是一条从“定义问题”到“工程落地”的完整链路。我这次最大的感受是：RAG 不是一个“向量库 + 大模型”的功能，而是一套需要持续归因、评测和调优的数据系统。

## 二、P2：RAG 的产品判断

### 1. RAG 的 R 是 Retrieval，不是 Vector

课程开篇就纠正了一个常见误解：RAG 不等于“向量数据库 + 相似度搜索 + LLM”。Retrieval 包含全文检索、向量检索、标量过滤、图谱跳转、API 工具调用等多种手段。

这让我重新理解了“AI 答得不好”的原因：问题不一定在模型，也可能在“取信息”的路径设计。一个好的 Agent 不是“更会答”，而是“更会找”。

### 2. 传统 RAG 与 Agentic RAG 的核心差别是“有没有循环”

传统 RAG 不一定简单，它也可以有改写、路由、多路召回、重排、压缩、引用等节点，但整体通常是一张预先设计好的有向无环图（DAG），走完就结束。

Agentic RAG 的关键变化是流程里出现了闭环：结果不够好可以再搜一次，搜索方式不对可以换一路，证据不够可以补搜，某个环节可以封装成工具按需调用。系统在运行时自己决定“要不要检索、先检索哪一路、一次够不够、要不要多跳、怎么合并证据”。

这对应到用户体验上，就是“按流程查了一遍”与“主动反复找、反复核对、反复修正”的差别。

### 3. 一条完整的 RAG 链路

P2 把 RAG 拆成六段：

**数据准备 → 问题理解与改写 → 搜索召回 → 融合重排 → 回答生成 → 评估反馈**

前三步决定“能不能找对”，后三步决定“能不能答对”。其中数据准备最容易被低估，却最影响最终效果：加载、解析、清洗、切分、元数据增强、建索引、更新策略，任何一环做差了，后面的混合检索都没有高质量数据可用。

### 4. 增强节点与演进路径

P2 介绍了几个常见增强节点：

- **Naive RAG**：搜一次、取 TopK、拼 Prompt、回答，简单但敏感。
- **Query Rewrite RAG**：先改写问题，让系统更会搜。
- **CRAG**：检索后先判断证据值不值得用，不够好就补搜或换源。
- **Self-RAG**：把“要不要检索、结果够不够、答案有没有证据支撑”部分内化到模型判断里。

这些节点说明：RAG 的演进不是“换一个更强的检索器”，而是在标准流程的不同位置不断插入判断、修正和反馈节点。传统 RAG 到 Agentic RAG 不是一道鸿沟，而是一条连续的演进路径：先把标准 RAG 跑通，再把搜索质量做好，然后补齐流程节点，最后才交给 Agent 编排。

### 5. 三层归因框架与决策树

这是 P2 最重要的部分。用户说“AI 答得不好”只是一个症状，根因可能在三层：

| 层级 | 典型表现 | 根因 | 解法 |
| --- | --- | --- | --- |
| 数据层 | 检索不到，或检索到错误内容 | 内容覆盖不足、数据准备差、检索路径设计有问题 | 补知识库、重做数据准备、混合检索、优化切分/改写/重排 |
| 模型层 | 检索到了正确内容，但回答无中生有 | 模型幻觉 | 引用来源设计、约束生成、信息不足时拒答 |
| 业务层 | 答案事实正确，但不符合业务场景 | 回答风格或业务规则不匹配 | 调整 System Prompt、补充业务规则 |

课程给了一个很实用的判断：**60%～80% 的“AI 答错了”其实在数据层，真正属于模型幻觉的通常只有 10%～20%。** 所以 PM 的第一反应不应该是“换模型”，而应该先问：知识库里有没有正确答案？AI 检索到了吗？模型有没有正确使用检索内容？

P2 还给了一棵四步决策树：先确认问题是什么；再检查知识库有没有正确答案；再检查 AI 有没有检索到；最后检查模型有没有正确使用检索内容。这样就把模糊的“AI 不行”变成了可执行的排查流程。

### 6. 混合搜索是 RAG 的底座

P2 认为混合搜索有三层价值：

1. 同时服务传统 RAG 和 Agentic RAG，让系统可以根据问题类型选择搜索方式；
2. 把复杂度内置到数据库层，减少开发者拼多套系统、手工对齐分值和排序的负担；
3. 支撑 Agentic RAG 的闭环编排，让“改写后再搜、先过滤再语义匹配、多路结果二次排序”在工程上可行。

所以混合搜索不是“高级玩法”，而是生产级 RAG 的基础设施。

## 三、I2：向量检索的工程原理

### 1. Embedding 与距离函数

Embedding 把文本、图片、音频等非结构化内容转换成固定维度的向量，把“内容是否相似”近似转化为“向量在高维空间中是否接近”。

但向量不是事实本身，它只适合做候选召回，不适合作为唯一证据。RAG 必须同时保存原文、来源、版本、权限和结构化元数据：向量负责“找到候选”，原文负责“提供证据”。

距离函数的选择要与模型训练方式匹配：

- **欧氏距离（L2）**：衡量绝对空间距离，受方向和模长影响；
- **余弦相似度**：关注方向、弱化模长，常用于文本语义检索；
- **点积**：同时受方向和模长影响；向量归一化后与余弦等价。

分数阈值不能跨模型照搬，“相似度大于 0.8 就算相关”不是通用规律，必须用当前业务数据校准。

### 2. 索引：KNN、ANN、HNSW、IVF、量化

精确 KNN 暴力扫描所有向量，结果精确但成本随数据量和维度增长，仍然是 ANN 评测的重要基线。

ANN 用少量召回损失换取延迟和吞吐收益，核心是三角权衡：**召回率、延迟/吞吐、资源成本**。没有在所有数据规模和负载下都最优的索引。

- **HNSW**：多层小世界图，适合低延迟、高召回的内存型检索；M、ef_construction、ef_search 都会影响召回与成本。
- **IVF**：先聚类分区，查询时只探测部分分区；nlist、nprobe 影响召回和延迟，数据分布变化后可能需要重建。
- **量化**：SQ、PQ、BQ 用精度换空间，常见做法是量化召回候选，再用原始向量精确重算。

### 3. 生产 RAG 的数据模型

一个可用于生产 RAG 的对象不应只有 ID 和向量，至少包含四类信息：

- **原始证据**：content、title、source_url，用于生成答案和展示引用；
- **向量**：embedding，用于语义召回；
- **业务元数据**：tenant_id、department、status，用于权限和业务过滤；
- **数据治理信息**：doc_version、chunk_no、content_hash，用于更新、追踪、去重和重建。

查询也往往不是“全库找相似”，而是在业务条件内找相似：`WHERE tenant_id = ... AND status = 'published'` 之后再按向量距离排序。

### 4. 离线与在线两条流水线

- **离线入库**：数据源 → 解析清洗 → 切分 → 元数据与权限补全 → Embedding → 写入正文/向量/索引 → 质量检查。
- **在线查询**：问题 → 查询理解或改写 → 查询向量化 → 多路召回 → 权限与业务过滤 → 融合重排 → 上下文组装 → LLM 生成 → 引用与答案验证。

离线流水线要保证幂等性，文档删除、更新、权限变化和模型升级都要有对应的维护策略。在线链路出问题时，要沿链路定位，而不是笼统归因于“大模型效果不好”。

### 5. 纯向量为什么不够

向量擅长语义近似，但真实业务还包含它不稳定的信号：错误码、订单号、型号、专有名词、租户/权限/时间/状态等硬约束、用户明确输入的关键词、最新版本优先等业务规则。

所以生产 RAG 通常组合三类检索：**向量检索、全文检索、标量过滤**。

标量过滤和向量检索的执行顺序也很关键：

- 过滤后精确计算：适合过滤后数据很少；
- 向量优先再过滤：适合过滤选择率高，但可能不足 K 条；
- 过滤下推 ANN：适合复杂权限和多种选择率，但实现和优化器更复杂。

“先向量 Top-10，再过滤权限”尤其危险：可能不足 10 条，还可能让无权限数据进入中间处理或日志。安全边界应尽可能在检索阶段生效。

不同召回器的分数量纲不同，不能直接相加。RRF 用名次融合，不要求向量距离和 BM25 分数可直接比较，是实用的融合基线。

### 6. 两阶段检索与上下文组装

召回阶段追求“不要漏掉”，重排阶段追求“把真正相关的放到前面”。

双编码 Embedding 可以提前离线生成文档向量，适合海量快速召回；Cross-Encoder 或重排模型让查询和候选共同参与计算，判断更细但成本更高。常见做法是：

```text
海量数据 → 低成本召回 50～200 条 → 重排模型精排 → 选 5～20 条进入上下文
```

候选数量不是越多越好，它会同时影响召回率、重排成本、延迟和上下文噪声。

上下文组装也不只是拼接：要去重、扩展父块或邻接块、恢复合理顺序、控制每个来源的 Token、保留来源和定位信息，还要防止知识库文本中的指令被当成系统指令执行（Prompt Injection）。

### 7. 评测：检索层、生成层、系统层

- **检索层**：Recall@K、Precision@K、MRR；有相关性等级时用 nDCG@K。
- **生成层**：忠实度、答案相关性、引用准确性、完整性、拒答能力。
- **系统层**：P50/P95/P99 延迟、吞吐、Embedding/重排成本、索引构建资源、写入后索引可见延迟、超时/降级/缓存命中率、租户隔离正确性。

“随机问几个问题看起来不错”不能支撑生产发布。评测集要覆盖高频、长尾、专有名词、错误码、跨段信息、无答案、权限隔离、时间敏感和对抗输入。

### 8. 专用向量数据库还是数据库向量扩展

业界有两条路线：专用向量数据库，和在现有数据库中扩展向量能力。

选型要看数据规模、查询负载、写入负载、混合查询、一致性、多租户安全、部署形态和团队成本。向量检索是核心负载、规模极大、需要专用索引时，优先评估专用系统；业务数据与向量、全文、权限过滤强耦合，希望用 SQL、事务和既有生态时，优先评估统一数据库。

**不要先选产品，再为产品寻找场景。**

## 四、P2 与 I2 的对应关系

| P2 的产品判断 | I2 的工程落点 |
| --- | --- |
| RAG 的 R 是 Retrieval，不是 Vector | 向量 + 全文 + 标量过滤 + 工具调用共同组成检索 |
| 传统 RAG 与 Agentic RAG 的差别是“有没有循环” | 查询改写、补搜、路由、融合重排、引用校验构成闭环 |
| 数据准备决定检索上限 | 离线流水线的解析、切分、元数据、幂等写入 |

| 混合搜索是 RAG 底座 | 向量 + 全文 + 标量 + RRF + 重排 |
| 先 Workflow 再 Agent | 从 Naive RAG 到增强 RAG，再到 Agentic RAG |

## 五、我的收获

1. **不要再把 RAG 等同于向量检索。** 向量只是 Retrieval 的一路。错误码、版本号、权限、时间这些精确信号，必须靠全文和标量过滤兜底。
2. **Agentic RAG 的关键不是更复杂，而是有循环。** 系统要能根据中间结果决定补搜、换路、重试，而不是沿着一张写死的流程图走完。
3. **大多数问题在数据层。** 以后遇到“AI 答得不好”，我会先走归因决策树：知识库有没有？检索到了吗？模型有没有正确使用？而不是先想着换模型。
4. **评测要跟流程走。** Context Recall 看召回有没有漏，Context Precision 看上下文干不干净，Faithfulness 看回答有没有忠于证据，Answer Relevancy 看有没有真正回答问题。四个指标分别对应流程的不同位置。
5. **选型由工作负载决定。** 统一数据库减少的是系统边界，不会自动消除索引设计、模型成本、权限治理和评测工作；组合式架构增加集成成本，但换取专业化扩展能力。两者没有脱离场景的绝对优劣。
6. **结合我自己的经历。** 我之前用 Opus 5.5 做实验，模型已经很强，但数据质量不高、标签也不是金标，效果就是上不去。P2 的归因框架和 I2 的评测方法正好解释了这个困境：问题不在模型层，而在数据层和评测口径。

| # | 现象 | 知识库有正确答案？ | 检索到了？ | 模型正确使用？ | 归因 | 解法 |

| 1 | 问 seekdb 1.2.0 的兼容性，回答成了 1.0.0 | 有 | 检索到旧版本，版本号被当成语义近似 | 是 | 数据层·检索策略 | 混合检索 + 版本元数据过滤 |

归因统计：数据层 3/5（60%），模型层 1/5（20%），业务层 1/5（20%）。和 P2 的判断一致：大多数问题在数据层。

### 2. I2：小规模检索对比实验

受仓库示例数据限制，本次用 `code/D3/data/knowledge_base.json` 的 19 条知识片段和 `evaluation_cases.jsonl` 中 50 条可回答案例做代理实验（文档数少于课程要求的 30 篇，结论只用于演示方法，不外推为生产性能）。

实验方法：

- **纯向量代理**：字符 3-gram + 英文 token 的 TF-IDF 余弦相似度，模拟语义向量召回；未调用真实 Embedding 模型。
- **纯全文**：BM25（k1=1.5，b=0.75）。
- **混合检索**：RRF（k=60）融合两路排名。
- 指标：Recall@1/3/5/10、MRR；P95 延迟为本机 20 轮 × 50 条查询的离线测量。

| 方案 | Recall@1 | Recall@3 | Recall@5 | Recall@10 | MRR | P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 纯向量代理 | 0.59 | 0.87 | 0.95 | 0.99 | 0.7704 | 0.047 ms |
| 纯全文 BM25 | 0.64 | 0.94 | 0.98 | 1.00 | 0.8479 | 0.262 ms |
| 混合检索 RRF | 0.66 | 0.96 | 1.00 | 1.00 | 0.8440 | 0.369 ms |

一个具体例子：查询 `E-4012` 时，纯向量代理 Top-1 是 `kb_018`，BM25 Top-1 是 `kb_006`，混合检索 Top-1 才是正确的 `kb_004`。这说明精确标识符场景下，混合检索能把全文的精确匹配和向量的语义召回结合起来。

观察：

- 混合检索把 Recall@5 从 0.95/0.98 提升到 1.00，说明两路召回互补；
- BM25 的 MRR 略高于混合检索，说明 RRF 不一定在每一个指标上都更好，融合后仍要看排序质量；
- 混合检索 P95 延迟约为单路的 1.4～7.8 倍（本机代理实验），生产中要结合候选数量和重排成本评估；
- 本次没有调整 Chunk 大小和 ANN 参数，这两项需要真实向量索引和更大数据，留待 D2/D3 或后续实验。

## 八、结论

Task 3 让我把 RAG 从“一个功能”重新理解成“一条数据链路”：产品侧要用三层归因框架定义问题和验收标准，工程侧要用混合检索、两阶段检索和分层评测把这条链路做扎实。

一句话总结：**RAG 的上限不只取决于模型，更取决于能不能把正确的信息找回来；而大多数时候，问题出在数据层，不在模型层。**
