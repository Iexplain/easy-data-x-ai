## 二、D2：AI 应用的数据层

### 1. 数据进库前的两步：切分与向量化

长文档不能整篇作为一个检索单元：语义会被稀释，命中后塞给模型的 Token 也太多。所以要先切成语义完整的片段，再逐段向量化。

固定大小 + 固定 overlap 是跑通原型的基线，但有三个进阶策略：

| 策略 | 核心思路 | 适合场景 | 主要代价 |
| --- | --- | --- | --- |
| 固定 overlap | 按字符数切，相邻块保留重叠 | 刚起步、文档量小 | 边界处容易切断语义 |
| 语义分块 | 按句子 Embedding 相似度找话题断点 | 话题跳跃的无结构长文 | 每句都要调 Embedding，成本高 |
| 动态 overlap | 标题、段落、表格、代码块边界加大重叠 | 已有固定分块但边界召回差 | 几乎零额外成本，性价比最高 |
| 父子 chunk | 子块检索，父块返回上下文 | 多跳推理、需要完整上下文 | LLM Token 消耗增加 |

我最大的感受是：**分块不是“越小越好”或“越大越好”，而是要把“检索粒度”和“生成粒度”分开考虑。** 父子 chunk 就是这种解耦：子块负责找得准，父块负责答得全。

### 2. Embedding 选型不是看排行榜

MTEB 排行榜适合缩小候选范围，但不能替代业务实测。更靠谱的方法是用 20–50 条真实 query 跑 Recall@K 和 MRR。

选型要看四个维度：

- **中英文能力**：中文企业文档里，bge-m3、通义 embedding 系列通常优于 OpenAI small；
- **多模态支持**：纯文本知识库不需要多模态；大量 PDF/图表才考虑 ColPali 或统一多模态向量；
- **成本**：不只看单价，还要看调用量、向量维度和部署方式；
- **延迟**：在线查询选 600M 参数以下的模型，离线批量入库可以用更大模型。

几个容易踩的坑：

- 入库和查询必须用同一个模型，否则向量空间不一致；
- query 和 document 的编码方式可能不同，比如 bge-m3 查询要加检索前缀；
- Embedding 负责初筛，Reranker 负责精排；
- 缓存和批量处理能显著降低成本。

### 3. 纯向量搜索的软肋

传统数据库擅长精确匹配，AI 应用需要语义匹配，所以向量搜索很有价值。但向量搜索理解“语义”，不理解“精确”：

- 错误码 E-4012 可能返回 E-4011、E-4013；
- 版本号 OB-4.2.1 可能返回 OB-3.x 或 OB-4.1.0；
- 配置项、参数名、精确数值都可能“语义相近但字面错误”。

这不是模型不够好，而是向量搜索方法论的固有边界。**精确匹配必须由全文搜索兜底。**

### 4. 混合搜索：一个引擎 vs 三个系统

混合搜索 = 向量搜索（语义）+ 全文搜索（精确）+ 关系过滤（结构化条件）。

行业常见做法是向量数据库 + 搜索引擎 + 关系数据库，再在应用层写胶水代码合并结果。这能跑通，但会带来：

- 三套部署、三套运维、三套 API；
- 数据同步延迟和一致性问题；
- 权限、租户、时间等过滤规则重复实现；
- 多路结果在应用层拼接、去重、排序，容易丢信息。

D2 的“三个厨房”类比很形象：三个厨房都能做菜，但协调成本是灾难性的。更合理的做法是一个引擎原生支持三种检索能力，在引擎内部完成融合排序。

这也是 I1 讲的“统一数据库 vs 组合式架构”在检索层的具体体现。

## 三、I3：SQL × AI

### 1. AI 函数不是普通 SQL 标量函数

`UPPER(title)` 和 `AI_COMPLETE('summary_model', content)` 看起来都是函数，但执行语义完全不同：

| 维度 | 普通本地函数 | 远程 AI 函数 |
| --- | --- | --- |
| 执行位置 | 数据库进程内 | 外部模型服务 |
| 延迟 | 微秒到毫秒 | 数十毫秒到数秒 |
| 确定性 | 相同输入通常相同输出 | 受模型、参数、服务状态影响 |
| 失败方式 | 类型或计算错误 | 网络、限流、超时、协议错误 |
| 成本 | CPU、内存、I/O | Token、请求、算力费用 |
| 事务回滚 | 计算本身无外部副作用 | 已发生的推理和计费不能回滚 |

核心心智模型：**AI_EMBED、AI_RERANK、AI_COMPLETE 是长得像 SQL 函数的远程网络调用。** AI_PROMPT 是例外，只在本地组装 Prompt JSON。

### 2. 四个核心函数

| 函数 | 输入 | 返回 | 是否调用外部服务 | 典型用途 |
| --- | --- | --- | --- | --- |
| AI_EMBED | 模型名、文本、可选维度 | 向量数组文本 | 是 | 文档和查询向量化 |
| AI_RERANK | 模型名、查询、候选、可选字段名 | JSON | 是 | 有限候选精排 |
| AI_COMPLETE | 模型名、Prompt、可选生成参数 | 长文本 | 是 | 摘要、抽取、分类、问答 |
| AI_PROMPT | 模板与参数 | Prompt JSON | 否 | 模板化组装 Prompt |

### 3. 执行链路：逻辑模型、端点与 Provider

一次 AI 函数调用通常经历：

参数求值 → 类型与值校验 → 模型解析 → 权限检查 → 端点解析 → 协议适配 → HTTP 调用 → 响应解析 → 返回 SQL。

SQL 里用稳定的**逻辑模型名**（如 `doc_embedding`），端点负责绑定 URL、Provider、凭据和物理模型名。这样换 URL、换凭据、换网关不需要改业务 SQL。

但换端点或物理模型不是“无影响的运维动作”：它可能改变向量空间、分数分布、输出格式和成本，必须进入模型变更与回归评测流程。

### 4. 成本、超时、重试与事务边界

一条 SQL 可能产生很多次远程请求。比如：

```sql
SELECT id, AI_COMPLETE('summary_model', content)
FROM knowledge
WHERE status = 'pending'
LIMIT 500;
```

最多可能产生约 500 次 Completion 请求，而不是 1 次。成本估算要按表达式实际求值次数算，不能按 SQL 语句数算。

重试带来一个关键语义：数据库无法确认超时前远端是否已经完成推理，所以一次 SQL 表达式可能产生重复推理和重复计费。应用层再重试整条 SQL，会和数据库内部重试相乘。

更重要的是：**AI 调用不属于数据库事务。** `ROLLBACK` 可以撤销本地写入，但撤不回网络请求、模型推理和费用。推荐的两阶段模式是：

```text
阶段 A：短事务读取与固化输入
  选择待处理行 → 保存输入版本、幂等键和任务状态 → 提交

阶段 B：事务外模型调用
  调用 AI 函数或模型 SDK → 校验结果 → 短事务写回
```

### 5. 安全与治理

I3 列了四类生产风险：

- **密钥泄露**：不把 access key 写进业务代码、截图或 SQL 日志；
- **敏感数据出域**：租户过滤只解决“哪些行能读”，不等于“可以发给外部模型”，还要做分类分级、脱敏和地域合规检查；
- **Prompt Injection**：检索到的文档是不可信数据，AI_PROMPT 只做字符串替换，不会清除恶意指令；
- **越权引用**：即使召回时过滤了权限，生成前仍要验证最终证据 ID 和版本对当前用户可见。

输出校验也要分两层：模型调用成功（HTTP/协议解析成功）不等于业务结果有效（JSON Schema、枚举、范围、业务规则通过）。

### 6. 适合与不适合 SQL × AI

适合：

- 在线查询只生成一次查询向量；
- 对有限候选做 Rerank；
- 对严格过滤后的小数据集做摘要、分类、抽取；
- 在统一数据上下文里组合关系、JSON、向量和模型结果；
- 小规模、可审计、失败边界清晰的 AI 加工。

不适合：

- 超大规模离线推理；
- 需要严格 checkpoint 的长任务；
- 多轮 Tool Calling 或复杂 Agent 状态机；
- 流式、多模态或完整 Chat 消息协议；
- 需要多端点负载均衡、熔断、自动容灾；
- 需要 exactly-once 外部调用；
- 要求外部推理随数据库事务一起回滚。

一个简单判断标准：**越靠近数据、集合越小、输入输出越结构化、失败边界越清楚，越适合进入 SQL。**

## 四、D2 与 I3 的对应关系

| D2 的工程判断 | I3 的落地方式 |
| --- | --- |
| 切分与向量化决定检索上限 | AI_EMBED 在入库/查询时生成向量，并记录模型版本 |
| 纯向量不够，需要全文和标量过滤 | SQL 中组合向量召回、全文候选、租户/权限/状态过滤 |
| 多路召回需要融合 | AI_RERANK 对有限候选精排，RRF/加权融合在 SQL 链路中完成 |
| 一个引擎优于三个系统拼凑 | AI Functions 让模型调用靠近数据，减少应用层搬运和关联 |
| 数据层要可治理 | 逻辑模型、端点、权限、脱敏、审计和可观测性 |

## 五、我的收获

1. **Chunking 是数据决策，不是参数玄学。** 先用固定 overlap 跑通，再根据边界召回问题选择动态 overlap；需要完整上下文时再上父子 chunk。
2. **Embedding 选型要用业务数据说话。** MTEB 只能缩小范围，最终要看自己数据的 Recall@K、MRR、延迟和成本。
3. **混合检索是生产级 RAG 的底线。** 纯向量在错误码、版本号、配置项这些精确信号上不可靠，必须让全文和标量过滤兜底。
4. **AI 函数不是免费的 SQL 语法糖。** 它带网络、成本、失败、重试和非确定性；事务回滚撤不回模型调用。
5. **先过滤，再调用；事务外调用，短事务写回。** 这是控制成本、延迟和事务风险的核心原则。
6. **越靠近数据、集合越小、失败边界越清楚，越适合 SQL × AI。** 复杂 Agent、流式、多模态、长任务还是留在应用层更合适。

### 2. I3：产品评论智能加工实验设计

设计一张评论表和三个逻辑模型：

```sql
CREATE TABLE product_reviews (
  review_id          BIGINT PRIMARY KEY,
  tenant_id          BIGINT NOT NULL,
  content            TEXT NOT NULL,
  content_hash       VARCHAR(128),
  embedding          VECTOR(1024),
  embedding_version  VARCHAR(64),
  summary            TEXT,
  processing_status  VARCHAR(32),
  updated_at         TIMESTAMP
);
```

实验步骤：

1. 注册 `review_embedding`（dense_embedding）、`review_reranker`（rerank）、`review_summary`（completion）三个逻辑模型及端点；
2. 选择不超过 20 条测试数据；
3. 用 `AI_EMBED` 生成评论向量，记录 `embedding_version`；
4. 对一个问题生成查询向量，按租户和状态过滤后召回候选，再用 `AI_RERANK` 精排；
5. 用 `AI_PROMPT` 组装“评论 + 证据 + 约束”，用 `AI_COMPLETE` 生成结构化摘要；
6. 对摘要做 JSON Schema 和业务规则校验；
7. 记录请求数、P95 延迟、重试次数和模型成本；
8. 模拟一次 429 和一次非法响应，验证失败状态不会污染正式数据；
9. 明确哪些步骤在事务内、哪些必须在事务外。

请求数估算：20 条评论 Embedding（20 次）+ 1 次查询 Embedding（1 次）+ 1 批 Rerank（1 次）+ 20 条摘要生成（20 次）≈ 42 次远程请求。如果 Rerank 候选超过单批上限，还要按批次数增加。

事务边界：

| 步骤 | 位置 | 原因 |
| --- | --- | --- |
| 选取待处理评论、写入输入哈希/幂等键/任务状态 | 事务内 | 短事务，保证任务可恢复 |
| AI_EMBED / AI_RERANK / AI_COMPLETE | 事务外 | 远程调用慢、可能重试、不可回滚 |
| 校验摘要并写回结果 | 事务内 | 短事务，保证结果一致 |
| 429 / 非法响应的重试与降级 | 事务外 | 避免长时间占用事务和锁 |

### 3. I3 思考题简答

1. **为什么 AI_COMPLETE 出现在 UPDATE 中会放大事务风险？** 等待模型会延长事务和锁持有时间；回滚撤不回推理和费用；重试或事务重放可能生成不同结果。
2. **同一查询向量为什么应先保存到变量？** 避免同一语句多处重复求值，导致重复调用模型服务。
3. **Rerank 对象数组为什么要保留 ID、版本和权限字段？** 便于把分数关联回原对象，并在生成前继续做权限和引用校验。
4. **数据库内部重试和应用重试叠加会怎样？** 重试放大、重复计费、延迟不可控，Completion 还可能返回不同文本；应统一最大尝试次数和预算。
5. **哪些模型配置变化会迫使重算历史数据？** Embedding 模型、版本、维度、归一化方式、query/document 编码方式变化；Rerank/Completion 变化通常需要重新评测，但不一定重算向量。
6. **什么情况下直接用模型 SDK 更合理？** 多轮 Tool Calling、流式输出、多模态、长任务 checkpoint、完整 Chat 协议、需要 exactly-once 或事务级回滚的场景。

## 八、结论

D2 让我理解了“数据层决定检索上限”：切分策略、Embedding 选型和混合检索，决定了 Agent 能不能拿到正确证据。I3 让我理解了“AI 调用进入 SQL 的边界”：AI 函数是远程网络调用，不是免费的 SQL 语法糖，必须用过滤、批处理、超时、重试和两阶段事务来治理。

一句话总结：**数据层要把“找得准”和“找得全”同时做好；AI 函数要把“能调用”和“可治理”同时做好。**
