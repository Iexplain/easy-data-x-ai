## 二、P3：Agent 记忆系统设计

### 1. 失忆的根因

上下文窗口就像一张工作台，每次新对话都会被清空。模型不是“忘了”，而是那些信息根本没有被保存到任何地方。

所以“AI 没有记忆”本质上是一个数据问题：模型只有训练数据，没有你的数据。记忆系统要做的，就是在模型之外，为每个用户建立一套持久的数据层。

### 2. CoALA 记忆分类

| 记忆类型 | 存什么 | 类比 | 举例 |
| --- | --- | --- | --- |
| 短期记忆 | 当前对话上下文 | 桌上的便利贴 | 这一轮对话里说过的话 |
| 语义记忆 | 事实和知识 | 百科全书 | “用户是 Python 开发者” |
| 情景记忆 | 过去的经历 | 日记本 | “上次用 Docker 方案解决了部署问题” |
| 程序记忆 | 行为规则 | 操作手册 | “回答代码问题时先解释再给示例” |

关键点：

- 短期记忆随会话结束消失；
- 语义记忆记录确定性事实；
- 情景记忆记录具体经历，常以 few-shot 示例发挥作用；
- 程序记忆是三种长期记忆中**唯一一种 Agent 可以自我修改的**，Skill 本质上就是被外部化、结构化的程序记忆。

### 3. 记忆的读写

写入有两种模式：

- **实时写入**：对话中主动判断“这条值得记住”，透明但占用推理资源；
- **异步写入**：对话结束后后台提炼，不干扰体验但有延迟。

读取不是按时间线翻历史，而是**基于语义搜索召回相关记忆**。这和 RAG 是同一个检索问题：RAG 从知识库检索文档，记忆系统从用户历史检索记忆。

### 4. 忘比存难：遗忘分数与分级处置

课程用艾宾浩斯曲线解释遗忘：

> **R(t) = e^(-λt)**

遗忘分数 = 初始权重 × 时间衰减。最终排名 ≈ 语义相关度 × 遗忘分数。

举例：假设 λ=0.05/天，7 天后保留率约 0.70，30 天后约 0.22，90 天后约 0.011。实际 λ 要按业务校准。

遗忘的核心动作不是删除，而是降权。分级处置：

| 处置 | 触发条件 | 系统行为 |
| --- | --- | --- |
| 降权（默认） | 分数下降但还没低到需要处理 | 保留在库中，检索排名自然靠后 |
| 归档 | 分数低于 0.3，或超过 30 天未访问 | 移出日常检索，但可查历史 |
| 硬淘汰 | 分数低于 0.1 且多次未被唤醒；或写入后 7 天从未使用 | 从存储中删除 |

被反复使用的记忆应该升到更高层级、衰减更慢。**遗忘不是事后补救，而是贯穿写入、存续、检索全流程的设计维度。**

### 5. 记忆冲突解决

先识别冲突形态：

| 冲突类型 | 举例 | 特征 |
| --- | --- | --- |
| 直接矛盾 | 爱喝咖啡，后来改喝茶 | 新旧互斥，必须二选一 |
| 时间演进 | 在用 Flask，后来改用 FastAPI | 版本更新，可合并 |
| 粒度差异 | 喜欢意大利菜，同时最近在吃素 | 可并存，检索时综合判断 |
| 历史与当前 | 去年负责人是 A，现在是 B | 两条都成立，适用时段不同 |

对应策略：

- **时间戳优先**：新信息覆盖旧信息，适合直接矛盾、时间演进；
- **置信度加权**：新旧并存，按新近度、确认次数、遗忘分数排序，适合粒度差异；
- **人工介入**：检测到冲突时询问用户，适合高敏感或系统不确定的场景。

处理时机也要配合：明确事实在写入时解决，复杂偏好在检索时按分数综合。

### 6. 用户信任与多 Agent 边界

好的记忆系统应该让用户：

1. 知道 AI 记住了什么；
2. 能修正错误记忆；
3. 能删除不想被记住的内容；
4. 理解记忆会如何影响 AI 的行为。

多 Agent 场景要回答“共享还是隔离”：

- 默认隔离，防止串味、保护隐私；
- 稳定用户画像可按用户共享；
- 同一项目内的 Agent 可按项目共享；
- 敏感记忆默认隔离，跨边界必须显式授权。

命名空间分三层：**用户 → Agent → 任务/项目**。在命名空间之上再加可见性：私有、组内共享、用户级共享。

课程引用的 LOCOMO 基准也很有说服力：有选择的记忆 + 时效衰减准确率 78.7%，把所有历史对话直接塞进上下文只有 52.9%。**全记不如会选择地记。**

## 三、I4：File SQL for AI Agent

### 1. File SQL 的定位

AI Agent 经常面对临时文件：用户上传的订单 CSV、日志 JSONL、分析系统导出的 Parquet。传统做法要经历“识别格式 → 推断 Schema → 建表 → 导入 → 查询 → 清理”，步骤多、失败点多、还产生数据副本。

File SQL 把文件直接解释为一条 SQL 里的**语句级临时关系**：

```sql
SELECT customer_id, SUM(amount) AS total_amount
FROM read_csv('/workspace/orders.csv')
GROUP BY customer_id;
```

没有 `CREATE TABLE`，没有 `LOAD DATA`，查询结束不留下持久表。

### 2. 三条路线与五步闭环

| 路线 | 优点 | 代价 | 适用场景 |
| --- | --- | --- | --- |
| 导入为普通表 | 完整事务与索引 | 步骤多、有副本、需清理 | 长期保存、反复查询 |
| 注册外表 | 不复制文件、可重复访问 | 仍需 DDL 与元数据治理 | 稳定数据源、共享访问 |
| 语句级文件关系 | 零建表、即时查询 | 只读、能力边界更窄 | Agent 临时分析 |

五步最小闭环：

1. **发现**：`glob('/workspace/*')`
2. **描述**：`DESCRIBE SELECT * FROM read_csv(...)`
3. **查询**：`read_csv` / `read_json` / `read_parquet`
4. **关联**：跨格式 `JOIN`
5. **导出**：`COPY (...) TO ... (FORMAT CSV, HEADER)`

### 3. 动态 Schema 与执行架构

SQL 编译期就要知道列名和类型，所以 File SQL 必须在编译阶段完成 Schema 推断：

```text
规范化路径 → 识别格式 → 读取表头/记录 → 累积候选类型
→ 合并为最终类型 → 构造语句级表定义 → 优化与执行
```

类型合并要确定性，例如：

- `NULL + BIGINT → BIGINT`
- `BIGINT + DOUBLE → DOUBLE`
- `DATE + DATETIME → DATETIME`
- 数字 + 普通字符串 → `VARCHAR`

关键不是“猜得聪明”，而是**同一文件在相同配置下始终得到相同结果和相同错误**。

执行架构：

```text
Parser → File Table Resolver → Path Guard + Schema Inferencer
→ Optimizer → Logical File Scan → Physical File Scan
→ CSV/JSONL/Parquet Reader → 类型化数据批次
→ Filter / Join / Aggregate / Sort
```

Reader 只负责文件 I/O、解析、类型转换、列裁剪；JOIN、聚合、排序必须由 SQL 引擎完成。不能把完整 SQL 旁路交给 DuckDB、SQLite、Polars 等外部引擎。

### 4. 一致性与路径安全

文件没有 MVCC。查询期间如果另一个进程覆盖、追加或替换文件，结果可能混合两个版本。

解决方案是文件指纹：

```text
device + inode + size + mtime_ns
```

任何关键字段变化都触发 `FILE_CHANGED`，整条 SQL 失败。即使客户端已经收到部分结果，也应视为无效。指纹只能检测变化，不等于事务快照；需要强快照时，先把数据导入正式表。

路径安全是 File SQL 的第一等能力：

- 默认关闭，要求配置 `secure_file_priv`；
- Path Guard：功能启用 → 根目录配置 → realpath → 是否在允许目录 → 是否普通文件 → 只读打开 → fstat 再校验；
- 拒绝 `..`、符号链接、目录/FIFO/Socket/设备文件、客户端同名路径；
- 限制单文件大小、列数、字段长度、JSON Key 数量；
- SQL 中的路径属于数据库服务器，不是发起查询的客户端电脑。

### 5. COPY TO 与 Agent 工具协议

COPY TO 的安全要求：

1. 输出路径也在允许根目录；
2. 默认不覆盖已有文件；
3. 先写同目录临时文件，成功后原子发布；
4. 失败、磁盘写满或取消时清理临时文件；
5. 表头、分隔符、引号、转义、NULL 与编码规则可复现；
6. 禁止把输出指向输入文件本身；
7. Agent 导出后验证文件存在、行数或摘要。

Agent 不应获得一个无限制的 `run_sql` 工具。更稳妥的协议是：

```text
list_allowed_files(pattern)
  → describe_file(path, format_options)
  → preview_file(path, limit)
  → query_files(sql)
  → export_query(sql, target)
  → verify_export(target)
```

操作准则：先发现再读取、先 DESCRIBE 再写 SQL、先小样本再全量、明确选择列、估算资源、错误即停止、导出用新文件名、记录审计信息。

## 四、P3 与 I4 的对应关系

| 维度 | P3 记忆系统 | I4 File SQL |
| --- | --- | --- |
| 数据生命周期 | 持久、跨会话 | 语句级、临时 |
| 主要操作 | 写入、检索、降权、冲突裁决 | 发现、描述、查询、连接、导出 |
| 安全边界 | 用户/Agent/任务命名空间 + 可见性 | `secure_file_priv` + Path Guard |
| 一致性 | 时效性、冲突裁决 | 文件指纹 + `FILE_CHANGED` |
| 用户信任 | 可查看、修正、删除记忆 | 只读、白名单、审计 |
| 核心难点 | 忘什么、怎么忘、给谁看 | 动态 Schema、路径安全、文件变化 |

两篇的共同判断是：**存储本身不难，难的是治理。** 记忆要治理时效、冲突和权限；文件要治理 Schema、路径和一致性。

## 五、我的收获

1. **记忆不是“把对话存下来”，而是“提炼事实 + 时效管理 + 冲突裁决”。** 全记不如会选择地记。
2. **遗忘是功能，不是缺陷。** 降权、归档、硬淘汰三级处置，比非删即留更接近真实助理。
3. **记忆冲突要先判形态，再选策略。** 直接矛盾走时间戳优先，粒度差异走置信度加权，敏感话题走人工介入。
4. **用户信任是多 Agent 记忆的前提。** 不能查看、修正、删除的记忆，功能再完善也很难被接受。
5. **File SQL 是“即时关系化”工具，不是数据库替代品。** 它适合一次性分析，不适合长期复用、强快照和复杂嵌套数据。
6. **File SQL 的安全是设计出来的。** 默认关闭、目录白名单、Path Guard、文件指纹、COPY TO 原子发布，缺一不可。
7. **Agent 工具协议要收窄。** 先发现、再描述、先预览、再全量，比给一个无限制的 `run_sql` 可靠得多。

## 七、课后行动

### 1. P3：记忆设计盘点

以我常用的 AI 助手为例，盘点用户每次都要重复提供的信息：

| 信息 | CoALA 分类 | 是否长期记住 | 衰减策略 |
| --- | --- | --- | --- |
| 角色：后端开发者 | 语义记忆 | 是 | 高初始权重，长期保留 |
| 技术栈：Python / FastAPI / PostgreSQL | 语义记忆 | 是 | 高初始权重，技术栈变化时更新 |
| 偏好：简洁回答、先给结论 | 语义记忆 | 是 | 高初始权重，多次确认后升层 |
| 项目背景：正在迁移到 AWS | 语义记忆 + 情景记忆 | 是 | 项目结束后归档 |
| 上次用 Docker 解决部署问题 | 情景记忆 | 是 | 按项目生命周期保留 |
| 回答代码问题先解释再给示例 | 程序记忆 | 是 | 长期保留，可根据反馈修改 |
| 今天心情不好 | 短期记忆 | 否 | 不写入长期记忆 |

五个设计问题的回答：

1. **哪些信息值得长期记住？** 稳定事实、长期偏好、项目关键决策、反复出现的约束；不记闲聊和一次性情绪。
2. **哪些应该随时间降权？** 临时任务状态、阶段性偏好、已结束项目的上下文；技术栈和角色变化时用新信息覆盖旧信息。
3. **冲突时用什么策略？** 明确变更走时间戳优先（Java→Go），并存偏好走置信度加权（喜欢意大利菜 + 最近吃素），敏感话题走人工介入（换工作、健康、财务）。
4. **用户如何管理记忆？** 提供记忆列表、逐条编辑/删除、解释“为什么这次推荐变了”；敏感记忆默认不写入。
5. **多 Agent 如何隔离/共享？** 默认隔离；稳定画像按用户共享；项目上下文按项目共享；敏感记忆私有，跨边界必须显式授权。

### 2. I4：File SQL 场景设计与测试

场景：用户上传 `orders.csv` 和 `customers.parquet`，要求“统计已支付订单的客户消费额，关联客户等级，导出前 100 名”。

操作流程：

```sql
-- 1. 发现文件
SELECT file FROM glob('/workspace/*');

-- 2. 确认结构
DESCRIBE SELECT * FROM read_csv('/workspace/orders.csv');
DESCRIBE SELECT * FROM read_parquet('/workspace/customers.parquet');

-- 3. 小样本验证 Join Key
SELECT o.order_id, o.customer_id, o.amount, c.level
FROM read_csv('/workspace/orders.csv') o
LEFT JOIN read_parquet('/workspace/customers.parquet') c
  USING (customer_id)
LIMIT 20;

-- 4. 执行并导出
COPY (
  SELECT o.customer_id, c.level, SUM(o.amount) AS total_amount
  FROM read_csv('/workspace/orders.csv') o
  LEFT JOIN read_parquet('/workspace/customers.parquet') c
    USING (customer_id)
  WHERE o.status = 'paid'
  GROUP BY o.customer_id, c.level
  ORDER BY total_amount DESC
  LIMIT 100
)
TO '/workspace/top_customers.csv'
(FORMAT CSV, HEADER);
```

安全与一致性检查：

- 文件必须在 `secure_file_priv` 白名单目录内；
- 拒绝 `..`、符号链接和特殊文件；
- 查询期间记录文件指纹，发生变化则 `FILE_CHANGED`；
- COPY TO 先写临时文件，成功后原子发布，不覆盖已有文件；
- 导出后验证文件存在、行数和摘要。

测试设计：

| 类别 | 测试点 |
| --- | --- |
| 正确性 | CSV/JSONL/Parquet 等价内容结果一致；投影、过滤、排序、聚合、JOIN、LIMIT |
| 鲁棒性 | CSV 引号/转义/字段内换行；JSONL 缺失字段/非法 JSON；Parquet 不支持类型/损坏 Footer |
| 安全 | `..`、符号链接、前缀碰撞、特殊文件、白名单外路径 |
| 一致性 | 编译后、执行前、执行中修改文件 |
| 导出 | 目标已存在、磁盘写满、查询失败、取消 |
| 架构 | EXPLAIN 中文件扫描是叶子算子，JOIN/AGG/SORT 由原生执行器承担 |

### 3. I4 思考题简答

1. **为什么 `read_csv(...)` 的 Schema 必须在 SQL 执行前确定？** SQL 编译、优化和结果列定义都需要列名与类型；客户端在第一行数据前就要拿到结果 Schema。
2. **只抽样前 1000 行推断类型，可能出现哪些不稳定结果？** 后面才出现的类型冲突、NULL、异常格式、前导零编码会被漏掉，导致结果随数据顺序变化；应使用确定性全量扫描或显式 Schema。
3. **文件查询过程中变化时，为什么“继续返回尽可能多的结果”不适合 Agent？** 结果可能混合两个文件版本，Agent 会基于不一致的数据做决策；应失败并等待文件稳定后重试。
4. **Reader 内部执行 JOIN 会破坏哪些架构边界？** 会让 Reader 承担 SQL 语义，导致优化器失效、格式扩展复杂、文件关系与普通表语义不一致。
5. **如何设计一个既方便 Agent 使用、又不能越过 `secure_file_priv` 的文件发现工具？** 只在白名单根目录内 glob，规范化路径并 realpath 校验，拒绝符号链接和特殊文件，只返回相对路径，不返回文件内容，并记录审计和资源限制。

## 八、结论

P3 让我理解了记忆系统的产品难点：不是“存”，而是“忘”、冲突裁决和用户信任。I4 让我理解了文件分析的工程难点：不是“能读文件”，而是动态 Schema、路径安全和文件变化下的一致性。

一句话总结：**记忆要会选择地记、按时间降权、按冲突裁决；文件要即时关系化、默认最小权限、变化即失败。**
